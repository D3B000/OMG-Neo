# 二分排查：递归分组与独立启停

界面采用「01 自由分支画布」的节点关系布局，按用户要求固定显示，不提供拖动或缩放。入口为「工具 → 二分排查」，保留 OMG-Neo 原有标题栏和底部导航。

## 使用方式

默认记录设置中的 GIMI\\Mods。也可先点击「更换目录」，用系统文件夹选择窗口指定本次排查目录；这不会修改全局 GIMI 设置。记录存续期间不能更换目录，请先恢复或结束记录。扫描时底边显示进度条，目录总量尚未确定时不显示百分比。

左上方是操作面板，当前组在画布中间，父组位于左下，同级另一组在当前组下方，两个子组向右展开。实线表示分组关系，虚线连接操作面板与当前组。画面最多显示五个分组节点，不随全树深度缩进或挤压。顶部路径栏返回祖先，深层路径折叠中间部分；「分组目录」以不缩进的列表支持跨分支跳转。「操作记录」同时展示初始快照并提供导出。长名称与目录路径省略显示，悬停查看完整内容。

点击「查看模组」打开当前组的独立滚动列表，再点击模组查看入口、目标与 INI 附属明细。目录和模组列表按需构建可见行，主画布不创建整棵树或全部模组行。画布位置与窗口尺寸成比例调整，960×540 下不会侵入底部导航区域。

记录、启停、撤销和恢复使用与其他页面相同的底部分段进度条。启停百分比按已改名并核验的入口数量更新，最终核验完成后显示完成；回退期间显示处理中状态。

1. 点击「记录已启用模组」。工具从资源浏览服务读取真实启停状态，记录初始已启用的模组，并立即均分为 A、B 两组。记录和分组不会改变任何模组的启停。
2. 操作面板用一个强调色长按钮切换当前组：全部启用时显示「停用本组」，部分启用或全部停用时显示「启用本组」，其他组保持原状。子组卡片也可直接启停该子组；「前往」只切换查看对象，不改变磁盘启停。
3. 选中 A，点击「继续二分」，得到 A1、A2；对 B 再操作一次，得到 B1、B2，总共四个末级组。
4. 每个子组仍可继续拆成两个子组。也可点击右下角「末级组再二分」，一次拆分全部可拆的末级组，从两组变四组、四组变八组。
5. 父组状态由其所有后代模组汇总，显示全部启用、全部停用或部分启用。停用 A 后仍可单独启用 A1，此时 A 显示部分启用，A2 与 B 保持原状。
6. 「撤销」只撤销上次启停，不撤销分组结构；「恢复初始状态」还原本次记录的初始启用状态并结束记录；「结束记录」保留当前启停与分组报告。

恢复成功或结束记录后，画布节点与当前计数清空，页面回到记录入口；原记录仍可通过操作记录导出。恢复失败时保留分组和恢复依据，便于处理冲突。重启后可在操作面板核对状态并继续分组。进度条铺满窗口底部，不受内容区左右留白限制。

页面按钮悬停时，强调色从左向右铺满；取消悬停时从右向左退出。按下提供同方向反馈，键盘焦点用边线标出；系统启用减少动态效果后直接切换状态。当前组顶部使用强调色条。父组从当前组与同级另一组之间连线的中心，经两个直角接入；底部「上一级」和「末级组再二分」同宽同高并对齐。目录与更换目录按钮固定在路径行最右侧。

组内只剩一个模组时不能继续二分；奇数数量尽量均分，例如 5 个分成 3 个和 2 个。分组是虚拟结构，不创建新目录，也不移动模组。

工具不启动或重载游戏，不要求退出游戏，不询问问题是否仍在，不建立基线或自动判定问题模组。游戏内操作与判断由使用者自行完成。如果系统因文件占用拒绝改名，工具报告实际文件错误，不强制解锁。

## 记录依据与明细

- 初始范围严格来自资源浏览服务 `ResourceService.listing` 返回的 `enabled`、`isMod` 与 `relativePath`，包括浏览页认可的 Junction 和联接内子模组。
- 初始停用项不进入分组；对根组执行启用也不会启用这些项。停用容器的子项不再纳入初始启用范围。
- 同一物理模组的多入口视为不可拆单元，防止只停用一个入口时另一入口仍然启用；同一物理目录的重复路径只执行一次改名。
- 点击右侧模组查看入口、目标、别名及 INI 明细；INI 是附属记录，不另定义启停、不按 INI 拆组，也不以其内容变化要求重新测试。
- INI 大小与 SHA-256 表示记录当时的元数据。附属明细读取失败时给出提示，模组仍按资源浏览页状态记录。
- 「操作记录」包含每次组启停与撤销，并提供导出 JSON。导出包括初始资源快照、完整分组树、精确操作日志与 INI 明细。

## 启停与恢复安全

- 保持原有启停方式：同一父目录精确改名，停用添加 `DISABLED `，恢复精确原名；不添加 `(n)`，不覆盖或删除任何模组。
- Junction 入口启停只改入口名；联接内子模组的改名会影响外部目标中的对应目录。
- 每次改名前保存操作意图，核验入口、父目录和联接目标身份后执行。批次出错会回退已执行的项，包括“改名成功但核验失败”的当前项。
- 原名和停用名同时存在、对象缺失或目标改变时，保留所有现有对象并停止，不猜测、不覆盖、不删除。
- 未结束记录持久保存。重启后可核对磁盘状态并继续使用原分组，或恢复初始状态。旧版引导流程的记录只提供安全恢复入口，不恢复旧版游戏确认流程。
- 日志完整性校验失败时只读阻断。跨便携实例按资源身份协调锁定，防止两个 OMG-Neo 实例同时修改同一批模组。
- 活跃记录期间，Neo 内其他资源启停、移动、归类、写回及业务配置修改被阻止；游戏启动入口不受分组阶段限制，主题调整和只读浏览仍可使用。
- 实际改名目前限本地 NTFS。系统权限或占用错误如实返回，不提权、不强制关闭进程。

本工具不读取、守护、覆盖或还原 `d3dx_user.ini`，也不把游戏写入配置作为继续分组的条件。恢复只恢复本工具拥有的名称变化，保留使用者在其他程序中编辑的内容。

## 文件位置

跟随 OMG-Neo 的 AppData / OMGNEO_DATA_ROOT：

```text
mod-bisect/
  integrity.key
  session.json
  <sessionId>-report.json
  report.json
```

前端：`lib/bisect_ui.dart`。后端：`backend/bisect_service.py`、`backend/bisect_fs.py`。

主要接口：`bisect.scan`、`split`、`splitLeaves`、`toggle`、`refresh`、`undo`、`resume`、`restore`、`finish`、`export`。没有 `confirmReload`、`result` 或自动排除候选的接口。

## 验证范围

临时文件测试覆盖：初始两组、递归四组／八组、两组独立启停、父停子启与混合状态、单模组叶节点、初始停用项保持原状、撤销与恢复、重启继续、真实 Windows Junction、重复入口、目标替换、重名冲突、改名后故障与日志失败。

原生窗口测试以确认稿为坐标基准，在 960×540 下核对三栏的顶部、底部、宽度和位置，并检查浅深主题、分组选择、独立启停请求和 INI 明细。测试不使用真实 Mods，不执行游戏操作。

本次验收：后端完整回归 137 项通过；Flutter 完整回归 68 项通过、2 项条件跳过；Flutter analyze 无问题。完整窗口测试核对原稿三栏坐标，冻结后端通过“记录两组 → 各组二分为四组 → 独立启停 → 恢复初始”的真实文件链路，无游戏确认步骤。
