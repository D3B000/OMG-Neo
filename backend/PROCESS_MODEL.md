# Neo 服务与注入端

`omg_backend.exe` 保持与 Flutter 的 stdio 协议连接，负责配置、资源管理、编译与更新。
只有收到 `launch.start`（启动游戏按钮）才启动 `omg_injector.exe --injector`。
启动应用、读取设置、浏览资源、重连服务均不会启动注入端。

注入端每次只执行一次启动任务，使用自己的 Qt 工作线程加载注入库，不执行注入校验。
两个 EXE 使用独立入口与依赖分析，继续共享冻结运行时和 DLL 目录。
`injector_main.py` 只导入注入流程；公共路径初始化放在 `backend_runtime.py`，避免反向导入服务端。
注入入口不包含资源管理、构建、更新和 requests/urllib3 等业务模块。
注入端不持有服务锁，也不继承服务的 stdio 协议管道。
`d3dx.ini` 中 loader 使用实际注入端的程序名。

服务在线程中监督注入端，用独立请求文件传递配置，并读取带任务 token 的原子结果文件。
必须同时满足进程退出码为 0 和有效完成结果，才能报告完成。
仅有退出码 0、非零退出、无效结果和超时均报告失败，常驻服务继续运行。
完成后删除请求文件，避免残留额外配置副本；结果和日志保存在运行数据目录。
关闭应用时异步结束本次注入端；90 秒超时也只结束本次注入端，不终止游戏。

`AppData/log/injection-lifecycle.jsonl` 记录服务 PID、注入端 PID、退出码和结果是否存在；
每次注入端的 stdout/stderr 单独写入 `injector-<任务ID>.log`。

之前的日志在等待游戏窗口阶段中断，已跳过注入校验，且系统未记录对应崩溃。
现有证据仍无法确认是哪一个原生调用导致退出码 0；DLL 导入退出函数并不能证明调用过它。
线程不能隔离进程级退出，因此改用独立进程将影响限制在单次启动任务内。
实际游戏和注入库未用于自动化测试，故不将模拟子进程测试视为真实游戏注入成功的证据。

分发构建使用 `omg_neo/build_release.ps1 -Configuration Release|Debug`。
Release 移除 UI 调整工具，Debug 保留；两个包均使用 krr.ico，只收集运行文件，排除个人配置和日志。

后端使用 `neo_hosts.spec` 分别生成两个 EXE，再通过一次 COLLECT 收集共享 DLL 与资源。
构建时检查注入依赖图，并对重复文件校验内容，发现同名不同内容的依赖立即失败。
两个分析可能产生不同的 base_library.zip；构建器合并字节码成员并检查冲突。
采用普通 onedir 模式，不引入需要跨 EXE 解压的 MERGE 或自定义 Python 启动器。
此前验证通过的软件 OpenGL 库和可选 PyOpenSSL/cryptography 分支已排除；Python 原生 TLS 库保留。

## 启动内存

首页连接后不再主动读取构建状态。构建服务仅在打开构建功能或收到构建请求时创建，
避免在启动阶段导入 alchemy、加载 ritual_bundle 和 Cython 分析库。
资源服务在第一次资源请求时创建，更新/下载模块在对应后台任务中导入。
构建页在连接准备好后读取状态，提前打开构建页也能在连接完成后继续加载。
大文件哈希使用流式读取，避免完整 DLL 的临时 bytes 副本。

`omg_neo/validation/measure_service_memory.py` 使用干净临时目录连续启动三次，
分别记录工作集、专用提交内存、专用工作集和历史工作集峰值。
`--eager-build` 用于模拟旧前端启动时立即请求构建状态的行为。
测量不调用工作集裁剪 API，不发网络请求，也不启动游戏。
编译、仪式执行期间的峰值不属于此启动内存目标。
